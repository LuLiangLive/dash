# 投研看板・功能链路与回归测试手册

> 适用版本：invest-v281（v2.9.12）

目的：为每次迭代 / 发布提供「一次改动、全链路回归」的操作指引 —— 明确每个**写操作**写到哪里、影响哪些页面、删除 / 撤销后哪些同步生效、哪些不会，以及改动一处后必须回归的关联链路。

使用方式：按 §3 分模块链路逐条执行；改动前查 §4 回归矩阵确定波及面。

**v2.9.5 功能链描述规范（全局强制，所有新增/修改功能链必须遵守）**：

每个功能链路必须包含 **5部分完整描述**，缺一不可：

| 部分 | 要求 | 目的 |
|------|------|------|
| ① 功能描述 | 一句话说明功能做什么 | 明确目标 |
| ② 正常路径 | Given-When-Then格式，包含数据断言（查数据库/API字段） | 验证主流程正确 |
| ③ 异常路径 | 至少3条（网络失败/服务端500/数据缺失/校验失败等） | 验证错误处理不静默吞掉 |
| ④ 边界条件 | 至少2条（空值/极值/状态切换/并发等） | 验证边界不崩溃 |
| ⑤ UI/数据规范 | 字号/间距/颜色/表单size/数据字段格式等 | 验证视觉一致性 |

**测试用例要求**：每条验收标准必须对应至少一个测试用例，测试用例必须包含：
- **数据断言**：直接查数据库或API返回字段，不只是看UI
- **UI断言**：检查DOM样式/布局/字号/间距
- **异常断言**：mock失败场景，验证用户能看到错误提示

**反模式（禁止）**：
- ❌ 只写"点击按钮→弹窗出现→toast成功"，不验证数据库/API数据
- ❌ 异常路径只写"失败时提示错误"，不写具体提示内容和数据状态
- ❌ 静默吞掉错误（catch后无任何用户提示或日志）
- ❌ 功能描述不完整导致测试目标错误（如只测正常路径不测异常路径）

## 1. 系统总览

### 1.1 架构



* **前端**：Vue3 + Vite + Naive UI，SPA **hash 路由**（`/#/xxx`），构建产物 `dist/` 拷入 `backend/static/`，随 backend 一起发布；静态资源前缀 `/static/`。

* **后端**：FastAPI + SQLite，业务路由 `/api` 与 `/api/advanced/*`，静态资源由 backend 托管（同源，无 CORS 问题）。

* **API Key**：本地部署已取消鉴权（`require_read_key=False`，v2.9.0），云端部署仍强制鉴权（`REQUIRE_READ_KEY=1`）。Key 存于 `localStorage.wb_api_key`，http.ts 自动为每个请求附加 `X-Touyan-Key` 头（⚠️ 不能用 `X-API-Key`—— 发布平台网关会剥离该标准头导致 401，实测定位）。密钥在 `backend/config.py` 的 `Settings.api_keys` 硬编码。未带 key 时读接口 401 / 写接口 401，页面会提示 "接口鉴权失败"。

## 2. 写操作 → 影响面速查矩阵

> 「反向」列回答：删除 / 撤销 / 清仓之后哪些会自动同步、哪些
>
> **不会**
>
> （即测试重点）。



| 操作（入口）                     | 主要 API                                                           | 写入表                                                                     | 立即生效的展示面                                             | 反向 / 删除后                                                                  |
| -------------------------- | ---------------------------------------------------------------- | ----------------------------------------------------------------------- | ---------------------------------------------------- | ------------------------------------------------------------------------- |
| 添加买入（详情页 / 添加弹窗）           | `POST /portfolio/investment`                                     | investment\_records + **recalc portfolio** + 当日收益快照幂等                   | 持仓列表卡片、详情汇总卡 (金额 / 份额 / 成本 / 收益)、记录列表、止盈汇总 (若有目标)、审计 | 删除该笔后 recalc → 汇总 / 记录回落；**profit 提醒规则不随单笔删除**（按 code 维度独立）               |
| 添加卖出（底部 / 点记录快速卖）          | `POST /portfolio/investment`(type=sell)                          | investment\_records + recalc                                            | 同上 + 该买入记录 FIFO 状态变灰（已卖出 / 部分）                       | 清仓后 portfolio 行删除→列表消失；详情页 isCleared 态；**profit 规则成为僵尸 (不再触发，仍显示)**       |
| 调整止盈（详情页底部「止盈」）            | `PUT /portfolio/investment/batch-target` + 前端 `alertsApi` upsert | investment\_records.profit\_target + alert\_rules(profit)               | 详情「预期收益」、记录「预期 %」标签、达标提示条、止盈汇总卡片、设置提醒列表              | 再调整→双写覆盖；在设置提醒**删规则** ≠ 清记录 profit\_target（记录标签仍显示）                       |
| 添加自选（顶部弹窗 / 榜单滑删 / 详情弹层）   | `POST /watch/add`(+`PUT /watch/sync`)                            | watchlist（可能 upsert funds）                                              | 自选页、首页缓存失效、提醒 price 扫 fund 范围扩大                      | 滑删有 5s 撤销；确认删除后自选页消失；**分组中该 code 仍在**                                     |
| 自选排序 / 清空 / 同步             | `PUT /watch/sync`                                                | watchlist 全表覆盖重建                                                        | 自选顺序                                                 | 覆盖式：任何旧状态直接替换                                                             |
| 删除分组                       | `DELETE /groups/{id}`                                            | watch\_group\_items 级联 + watch\_groups                                  | 分组列表                                                 | 组内基金回到未分组，**不删除自选**                                                       |
| 创建 / 修改 / 删除提醒规则（设置提醒 tab） | alertsApi CRUD                                                   | alert\_rules                                                            | 规则列表                                                 | 删除规则即永久失效，历史保留                                                            |
| 删除整支持仓（详情页原删除 / 无入口则 API）  | `DELETE /portfolio/{code}`                                       | investment\_records + portfolio + **同 code profit 规则**                  | 持仓列表消失                                               | 完整级联；自选 / 提醒其他类型规则**不受影响**                                                |
| Excel / 截图导入（下拉「操作」）       | `POST /import/excel`、`/ocr-upload`                               | investment\_records + recalc                                            | 持仓列表 / 记录 / 汇总                                       | 重复导入不幂等（无去重），需按日期人工核对                                                     |
| 数据导出                       | exportApi                                                        | 无（读 + 下载）                                                               | 文件                                                   | —                                                                         |
| 多设备同步导入                    | `POST /sync/import`                                              | watchlist/groups/portfolio/records/rules/settings **INSERT OR REPLACE** | 各对应页面                                                | **导入 investment\_records 不触发 recalc** → 需同时导入 portfolio 汇总，否则汇总与实际记录可能不一致 |

#### 链路 A：买入 → 生效点全量核对

**功能描述**：用户在持仓详情页或持仓管理页添加买入记录，系统更新持仓汇总、记录列表、止盈目标（如有），并自动补全净值。

**正常路径（Given-When-Then）**：
- Given 用户已登录，基金022364已有持仓（或空仓）
- When 用户在详情页底部点击「买入」（或持仓管理页「添加投资」）
- And 填写日期（YYYY-MM-DD）、金额、净值、份额，可选填写止盈目标%
- And 点击「确认」
- Then 调用 `POST /portfolio/investment` 成功
- And toast显示「买入成功」
- And 详情页汇总卡：金额/持有份额/成本价增加，收益按当日快照净值重算
- And 记录列表新增一笔，状态标签=「持有中」（红色），日期=所选日期
- And 若填写止盈目标>0：详情「预期收益」显示该%，记录带「预期 X%」标签，止盈汇总卡片多一笔
- And 返回持仓管理页：卡片总份额/金额更新，顶部总览3卡更新
- And 数据断言：investment_records表新增type='buy'记录，profit_target=填写值（如有）

**异常路径**：
1. **净值缺失**：
   - When 填写的日期在nav_history表中无净值记录
   - Then 系统自动从nav_history/实时源补净值
   - And 若补净值失败，返回400错误，**不落库**，弹窗不关并显示错误提示
2. **金额份额同时为0**：
   - When 买入金额和份额都填0
   - Then 返回400错误，提示「金额和份额不能同时为0」，不落库
3. **日期格式错误**：
   - When date字段传时间戳而非YYYY-MM-DD字符串
   - Then 返回422错误，提示日期格式错误
4. **服务端500错误**：
   - When API调用失败（网络错误/服务端异常）
   - Then toast显示「买入失败，请稍后重试」，记录列表不新增，汇总卡不更新

**边界条件**：
1. **空仓首次买入**：持仓管理页无该基金卡片，买入后新增卡片，顶部总览基金数+1
2. **止盈目标=0或空**：不创建alert_rules记录，止盈汇总卡片不增加，记录不带「预期X%」标签
3. **反向删除**：无单条删除UI入口（API存在）；删除整持仓→记录+汇总+profit规则全清（§3.3）

**UI/数据规范**：
- 买入弹窗表单size=small，输入框高度32px，圆角8px
- 标签字号12px/500，输入字号13px，表单项间距14px
- 「持有中」状态标签：红色背景（rgba(220,38,38,0.08)）+ 红色文字（#dc2626），字号10px，padding 1px 6px，圆角4px
- 记录卡片左侧色条：买入=红色（3px solid var(--up-light)）
- 数据字段：date必须YYYY-MM-DD，amount>0，shares>0，nav>0，profit_target可选>0

#### 链路 B：卖出 → 状态与清仓联动

**功能描述**：用户卖出持仓，系统按FIFO（先进先出）抵扣最早买入记录，更新持仓状态（持有中/已卖出），清仓后基金从持仓列表消失。

**正常路径（Given-When-Then）**：
- Given 用户已登录，基金022364有持仓且持有份额>0
- When 用户在详情页底部点击「卖出」（或点击买入记录快速卖出=全部份额预填）
- And 填写卖出金额/份额，点击「确认」
- Then 调用 `POST /portfolio/investment`(type=sell) 成功
- And toast显示「卖出成功」
- And 记录列表新增卖出记录（红条+「已卖出」灰标签）
- And 被卖出的最早买入记录按FIFO抵扣：
  - 全部清光→灰条+「已卖出」+浮动收益淡化（opacity 0.45）
  - 部分卖出→仍「持有中」（剩余份额>0）
- And 汇总卡份额/金额同步减少
- And 若持仓清零：持仓管理页该基金消失（portfolio行删除），详情页进入isCleared态（底部操作栏隐藏、卡片置灰）
- And 数据断言：investment_records表新增type='sell'记录，被抵扣的buy记录status更新为'sold'（全部清光）或'partial'（部分）

**异常路径**：
1. **卖出份额>当前持有**：
   - When 填写的卖出份额大于当前持有份额
   - Then 返回400错误，提示「卖出份额不能超过持有份额」，弹窗不关，不落库
2. **空仓卖出**：
   - When 基金持有份额=0时点击卖出
   - Then 底部操作栏隐藏（isCleared态），无法点击卖出按钮
3. **服务端500错误**：
   - When API调用失败
   - Then toast显示「卖出失败，请稍后重试」，记录列表不新增，汇总卡不更新

**边界条件**：
1. **全部卖光后profit提醒规则仍保留**：该基金的profit类型alert_rules记录仍在「设置提醒」列表（成为不再触发的僵尸规则），需手动删规则或删除整持仓清理
2. **多笔买入部分卖出**：按FIFO抵扣最早的买入记录，先清光最早的，再抵扣下一笔，状态分别标记
3. **卖出金额份额同时为0**：返回400错误，与买入相同校验

**UI/数据规范**：

#### 链路 C：止盈设置 / 调整 → 双写一致性与实时性

**功能描述**：用户设置或调整基金的止盈目标，系统同时更新investment_records表的profit_target字段和alert_rules表的profit类型规则，确保双写一致，达标后触发提醒。

**正常路径（Given-When-Then）**：
- Given 用户已登录，基金022364有持仓
- When 用户在详情页底部点击「止盈」

- And 用户输入新目标6%，点击「确认」
- Then 调用 `PUT /portfolio/investment/batch-target`（单条SQL原子更新全部buy记录）
- And 前端同步调用 `upsertProfitRule(target)` 创建/更新alert_rules记录

- And 数据断言：
  - investment_records表中该基金所有type='buy'记录的profit_target=6（全部一致）
  - alert_rules表中存在type='profit' AND code='022364'的记录，threshold=6，enabled=1

**异常路径**：
1. **alert_rules同步失败**：

   - And 详情「预期收益」不变

4. **服务端500错误**：
   - When API调用失败
   - Then toast显示错误提示，不更新任何数据

**边界条件**：
1. **已有同基金profit规则**：更新threshold和enabled=1，不创建重复记录（按type='profit' AND code=基金代码判断已存在）
2. **多只基金设置止盈**：每只基金对应一条alert_rules记录，互不影响
3. **手动在提醒中心删除profit规则**：规则消失，但investment_records的「预期%」标签仍在，之后自动check不再触发该基金止盈提醒（已知不一致点）
4. **再调整目标**：两条数据源（investment_records + alert_rules）都被覆盖，无残留旧值，批量接口保证全部记录profit_target相同

**UI/数据规范**：

- 数据字段：profit_target>0才同步alert_rules，threshold=profit_target，condition='above'，type='profit'

### 3.5 提醒链路

**功能描述**：提醒系统支持4类规则（score/price/signal/profit），后端事件中枢每5分钟自动扫描，命中后写入alert_history并更新未读角标，支持已读/全部已读/删除历史。

**规则类型表**：

| 类型 | 作用域 | condition | 触发条件 |
|------|--------|-----------|---------|
| score | 全局(无code) | above | 任一基金综合分≥阈值 |
| price | 全局 | above/below | 日涨幅d1≥阈值/≤-阈值 |
| signal | 全局 | 忽略 | funds.reco≠prev_reco（信号变化） |
| profit | 单基金(有code)/全局 | above | 对应持仓收益率≥阈值 |

#### 链路 B：提醒触发与扫描

**功能描述**：后端事件中枢每5分钟自动扫描启用的规则，命中后写入alert_history并更新未读计数，同一rule+code 1小时内不重复触发。

**UI/数据规范**：
- 扫描频率：后端事件中枢每5分钟自动扫描
- 去重窗：1小时（3600秒），按rule_id+code去重

#### 链路 C：超跌筑底榜

**功能描述**：超跌筑底榜筛选"短期急跌→处于低位→RPS弱势→筑底企稳"的基金，按反弹预期排序，核心形态四段式：急跌+低位+RPS弱势+筑底。v2.9.11加入RPS相对强度指标，v2.9.12加入均线粘合加分（MA5/MA10/MA20差距<2%，低位震荡时额外加分）。综合评分权重：急跌程度20 + RPS弱势10 + 低位程度25 + 筑底信号35 + 赛道景气10。

**正常路径（Given-When-Then）**：
- Given 用户已登录，榜单数据已采集，nav_history有60日数据
- When 用户切换到推荐榜单→超跌筑底子榜

- And 每只基金卡片显示「筑底阶段」标签（已反弹/反弹后回调/低位震荡/二次探底/创新低/下跌中，6种颜色）
- And 低位震荡且均线粘合（MA5/MA10/MA20差距<2%）的基金额外加分
- And 评分显示为卡片综合分（0-100），权重：急跌程度20 + RPS弱势10 + 低位程度25 + 筑底信号35 + 赛道景气10
- And 数据断言：入榜基金满足急跌（三信号任一）+低位（距60日高点回撤≤-20%或60日分位≤20%）+RPS弱势（60日相对强度<30%），评分降序

**异常路径**：
1. **nav_history数据不足**：
   - When nav_history表数据不足60日
   - Then 急跌/低位/筑底指标计算不准确，榜单可能为空，提示「数据不足，请先一键更新」
2. **无符合条件的基金**：
   - When 市场整体上涨，无基金符合急跌+低位条件
   - Then 榜单显示空态提示「暂无超跌筑底基金」
3. **计算失败**：
   - When _compute_crash_bottom_panel()计算失败
   - Then 记录错误日志，榜单显示错误提示

**边界条件**：
1. **急跌判定（三信号任一）**：
   - 信号1·波动率倍数法：近20日累计跌幅 ≥ 20日正常波动幅度(vol_60d×√20) × K（默认K=2.0，可配1.5~3.0）
   - 信号2·短期加速下跌法：近5日跌幅 ≥ 近60日滚动5日涨跌幅绝对值均值 × 1.5，且近5日跌幅贡献近20日跌幅大头
   - 信号3·历史分位法：近20日跌幅 ≤ 全市场近20日涨跌幅的5%分位数（极端尾部）
2. **急跌强度分级（v2.9.11调整为20分）**：轻度急跌（命中1信号，10分）/ 中度急跌（命中2信号，15分）/ 重度急跌（命中3信号，20分）
3. **RPS相对强度判定（v2.9.11新增，入榜硬条件）**：
   - RPS计算：对全量基金池的60日涨跌幅排序，RPS = 比它弱的基金数 / 总数 × 100（0%=全市场最弱，100%=全市场最强）
   - 入榜条件：RPS_60d < 30%（可配cd_rps_threshold，默认30%），确保是真超跌而非正常回调
   - RPS弱势评分（10分）：RPS越低分越高（0%→10分，30%→0分，线性插值）
   - RPS回升加分：若RPS_20d > RPS_60d + 10百分位（可配cd_rps_rebound），筑底分+3（上限35分）
4. **低位判定（满足任一）**：距60日高点回撤 ≤ -20%（可配）或 60日净值分位 ≤ 20%（可配）
5. **筑底阶段（6级，按优先级匹配）**：已反弹（35分）/ 反弹后回调（30分）/ 低位震荡（28分，波动率收窄）/ 二次探底（20分）/ 创新低（10分）/ 下跌中（5分）
6. **综合评分（0-100，v2.9.11调整）**：急跌程度20分 + RPS弱势10分 + 低位程度25分 + 筑底信号35分 + 赛道景气10分（默认5分），按评分降序，同分按近60日跌幅绝对值降序
7. **数据周期说明**：因现有nav_history仅约100交易日，方案中120日/250日指标均用60日代替
8. **参数可调**：我的→算法→超跌筑底榜，修改cd_crash_k/cd_accel_ratio/cd_low_dd/cd_low_pct/cd_vol_narrow/cd_topn/cd_rps_threshold/cd_rps_rebound后重算榜单
9. **输出字段（v2.9.11新增）**：rps_20d（20日相对强度百分位）、rps_60d（60日相对强度百分位）

**UI/数据规范**：
- 急跌级别标签：轻度=橙色背景(#FF9800)+白字，中度=红色背景(#E53935)+白字，重度=深红色背景(#B71C1C)+白字，字号10px，padding 1px 6px，圆角4px
- 筑底阶段标签：已反弹=绿色背景(#C6EFCE)+深绿字，低位震荡=黄色背景(#FFEB9C)+深黄字，二次探底=橙色背景(#FFC000)+白字，创新低=红色背景(#FF6B6B)+白字，下跌中=深红背景(#C00000)+白字，字号10px

- 后端计算入口：`rank_full.py::_compute_crash_bottom_panel()`，在`_compute_reco_panels()`中调用

#### 链路 E：动能标签4档机制

#### 链路 F：持仓标签三级降级机制

**功能描述**：基金卡片底部的持仓标签（themes）采用三级降级机制：真实持仓抓取→名称推断→兜底标签，减少兜底标签比例。

**正常路径（Given-When-Then）**：
- Given 用户已登录，一键更新已完成
- When 查看基金卡片的持仓标签
- Then 优先显示真实持仓标签（如"半导体45%"）
- And 真实持仓抓取：一键更新阶段2.5调用`_fetch_top_holdings()`，抓取上榜+自选基金的十大持仓，经`holdings_themes()`归类为行业/概念标签
- And 若持仓抓取失败，降级1：调用`sector.infer_themes()`从基金名称推断（优先级：具体指数名 > 行业关键词 > 板块兜底）
- And 若名称无法匹配，降级2：标记为"核心资产"（兜底标签）
- And 数据断言：榜单前20只基金中，"核心资产"兜底标签占比应 < 30%

**异常路径**：
1. **持仓抓取失败**：
   - When _fetch_top_holdings()调用失败（网络错误/接口限流）
   - Then 降级为名称推断，若名称推断也失败则降级为兜底标签
   - And 记录警告日志，不影响其他基金
2. **持仓占比过低**：
   - When 十大持仓合计 < 5%（ETF联接基金主要持有母基金，股票持仓是噪音）
   - Then 返回空标签，不显示持仓标签
3. **重复抓取**：
   - When stocks字段非空的基金重复抓取
   - Then 断点续传：检查stocks字段非空则跳过，避免重复抓取，一键更新日志中显示"跳过"数量

**边界条件**：
1. **三级降级机制**：
   - 真实持仓（优先）：抓取上榜+自选基金的十大持仓，经holdings_themes()归类
   - 名称推断（降级1）：持仓抓取失败时，从基金名称推断（具体指数名 > 行业关键词 > 板块兜底）
   - 兜底标签（降级2）：名称无法匹配任何行业时，标记为"核心资产"
2. **断点续传**：_fetch_top_holdings检查stocks字段非空则跳过，避免重复抓取
3. **持仓占比阈值**：十大持仓合计 < 5% 时返回空（ETF联接基金主要持有母基金，股票持仓是噪音）
4. **验证标准**：榜单前20只基金中，"核心资产"兜底标签占比应 < 30%；超过则说明持仓抓取失败，需重新运行一键更新
5. **真实持仓验证**：ETF/指数基金的持仓标签应与跟踪指数一致（如半导体ETF显示"半导体"）
6. **名称推断验证**：主动基金名称含行业关键词时应显示对应行业（如"医疗健康混合"显示"医药"）

**UI/数据规范**：
- 持仓标签：最多3个，含持仓百分比（如"半导体45%"），字号10px，padding 1px 6px，圆角4px，不同行业不同颜色
- 兜底标签"核心资产"：灰色背景+灰字，与真实持仓标签区分
- 数据字段：themes为JSON数组，每个元素含name和percent，stocks为十大持仓JSON

#### 链路 A：一键更新数据

**功能描述**：用户手动触发一键更新，FetchManager执行八阶段流程（日期判断→抓净值（含历史数据补全+多源并行）→抓取补充数据→重排榜单→计算榜单指标→计算自选指标→算推荐信号→同步榜单），完成后自动刷新全站数据。v2.9.14起，净值抓取阶段自动判断历史数据缺口，缺口>1000只时触发多数据源并行（同花顺+pingzhong+天天基金），并进行数据准确性验证（异常值检测+日期连续性检查）。

**正常路径（Given-When-Then）**：
- Given 用户已登录，进入「我的→运行」
- When 用户点击「一键更新数据」
- Then 调用`POST /fetch/start`成功
- And FetchManager执行八阶段：
  1. 日期判断：检查哪些基金的缓存需要更新
  2. 抓净值：增量抓取净值数据（v2.9.14起自动判断历史数据缺口，<250天的基金触发补全；缺口>1000只时多数据源并行抓取；抓取后进行异常值检测和日期连续性检查）
  3. 抓取补充数据：持仓 + m3/m6/y1 + 2年历史净值（自选+上榜基金）
  4. 重排榜单：全量重算10个sub榜单（此时m3/m6/y1已是最新）
  5. 计算榜单指标：榜单基金的完整指标计算
  6. 计算自选指标：自选基金的完整指标计算
  7. 算推荐信号：计算推荐信号和评分
  8. 同步榜单：同步榜单数据到前端
- And 进度2s轮询，前端显示当前阶段和进度百分比
- And 完成后：终态写data_update_logs（success/failed/cancelled），done另写meta.rank_recomputed_at时间戳
- And 数据版本戳自动更新（bump_data_version），通知前端缓存失效
- And 各开着的页面60s内自动刷新榜单/日期/自选并toast提示「数据已更新」
- And 数据断言：rank_snapshots表新增当日数据，funds表净值更新，data_update_logs有success记录，settings表data_version已更新

**异常路径**：
1. **非交易日**：
   - When 一键更新在非交易日触发
   - Then 日期判断阶段检测为非交易日，提示「今日非交易日，使用最近交易日数据」，继续执行或跳过
2. **部分阶段失败**：
   - When 某个阶段（如抓净值）失败
   - Then 记录错误日志，继续执行后续阶段（或中止，取决于失败严重程度）
   - And data_update_logs记录failed，前端显示「部分数据更新失败」
3. **用户中断**：
   - When 用户点击「停止」按钮
   - Then `stop`协作中断，当前阶段完成后停止，data_update_logs记录cancelled
   - And stopped不应触发自动刷新
4. **网络错误**：
   - When 抓净值时网络错误
   - Then 重试3次，仍失败则记录错误，继续后续阶段
5. **数据版本戳更新失败**：
   - When 数据版本戳更新失败
   - Then 记录警告日志，不影响主流程，前端可能需要手动刷新

**边界条件**：
1. **采集无定时**：全量净值采集不内嵌、不依赖外部cron（不再有每日20:45定时采集），仅由手动触发。v2.9.3起后端有内嵌事件中枢（services/event_hub.py），但其调度范围仅提醒规则扫描与资讯三档采集，不触发净值采集
2. **完成联动**：跑完一次一键更新，停在榜单页不改选1分钟内数据应自动变化（榜单快照日期/更新时间）；stopped不应触发自动刷新
3. **进度轮询**：进度2s轮询，前端显示当前阶段名称和进度百分比（0-100%），共8个阶段节点
4. **重复触发**：一键更新运行中再次点击，提示「正在更新中，请稍候」，不重复触发
5. **空库首次更新**：空库首次一键更新时间较长（需抓取所有基金净值），进度显示正常
6. **抓取补充数据阶段**：该阶段在重排榜单之前执行，确保重排榜单时m3/m6/y1是最新的；抓取自选基金 + 上一次上榜基金的补充数据
7. **v2.9.8 动态候选池**：补全2年历史净值的候选池从"上榜+自选"扩大为"上榜+自选+当日涨幅前100+当日跌幅前100"，让新基金有机会获得完整数据，解决"榜单自增强"问题

#### 链路 B：运维动作

**功能描述**：提供危险区运维动作（recompute-all/clear-cache/reset-snaps），影响面不同，需谨慎操作。

**正常路径（Given-When-Then）**：
- Given 用户已登录，进入「我的→数据→危险区」
- When 用户点击某个运维动作（如recompute-all）
- And 确认弹窗提示影响面
- And 用户点击「确认」
- Then 执行对应运维动作
- And audit_logs记录该操作
- And 数据断言：对应数据表被清空或重建

**异常路径**：
1. **用户取消**：
   - When 用户在确认弹窗点击「取消」
   - Then 不执行任何操作，返回原页面
2. **执行失败**：
   - When 运维动作执行失败（如数据库锁定）
   - Then 记录错误日志，toast显示「操作失败，请稍后重试」，数据不变化
3. **权限不足**：
   - When 普通用户尝试执行运维动作
   - Then 返回403错误，提示「权限不足」

**边界条件**：
| 动作 | 影响 | 回归点 |
|------|------|--------|
| recompute-all | 与一键更新相同全量重建 | 榜单/评分/详情数据刷新 |
| clear-cache | DELETE nav_history + 删缓存文件 | 净值走势/详情暂时空白直至重建；自选/持仓汇总字段不受影响（存portfolio表） |
| reset-snaps | DELETE rank_snapshots | 榜单历史日期列表清空，需重排 |

1. **审计日志**：自选/持仓/配置/算法/运维写操作均记audit_logs + audit.log文件；无清理接口
2. **clear-cache不影响持仓**：清空nav_history后，自选/持仓汇总字段不受影响（存portfolio表），只有净值走势/详情暂时空白
3. **reset-snaps需重排**：清空rank_snapshots后，榜单历史日期列表清空，需重新运行一键更新或recompute-all重排

**UI/数据规范**：
- 运维动作入口：「我的→数据→危险区」，红色警告样式
- 确认弹窗：显示动作名称/影响面/警告提示，确认按钮红色
- 数据字段：audit_logs含action/user_id/timestamp/details，不可删除

#### 链路 C：数据一致性与统一取值优先级

**功能描述**：确保基金卡片、基金详情弹窗、对比页面三个页面的同一个指标显示相同数值，统一所有指标的取值优先级和计算口径。

**核心设计**：
1. **统一数据源**：三个页面都优先从funds表读取预计算指标，只有当funds表中没有值时才实时计算
2. **统一取值优先级**：m1/m3/m6/y1优先从pingzhongdata接口获取，失败时用净值序列计算兜底
3. **统一计算口径**：卡玛比率=2个月收益/近2月最大回撤，所有页面使用相同口径
4. **数据完整性检查**：数据不足窗口80%时返回None，不显示错误数值
5. **数据版本戳**：一键更新完成后自动更新版本戳，通知前端缓存失效

**正常路径（Given-When-Then）**：
- Given 用户已完成一键更新，funds表中有完整的预计算指标
- When 用户打开基金卡片、基金详情弹窗、对比页面
- Then 三个页面的同一个指标（如m3、calmar、max_dd）显示相同数值
- And 数据断言：三个页面调用的API返回的指标值相同，都来自funds表
- And 卡玛比率=近2月收益/近2月最大回撤，分子分母时间周期匹配
- And 数据不足时（如成立不足1年的基金），y1显示"—"而不是错误数值

**异常路径**：
1. **funds表中没有指标值**：
   - When funds表中某个指标为None
   - Then 弹窗/对比页面调用inject_long_metrics实时计算
   - And 实时计算优先从pingzhongdata接口获取，失败时用净值序列兜底
2. **pingzhongdata接口失败**：
   - When pingzhongdata接口请求失败
   - Then 用净值序列计算兜底，记录警告日志
   - And 用户看不到错误，指标正常显示
3. **数据不足**：
   - When 基金成立不足1年，计算y1需要252天数据但只有100天
   - Then 返回None，前端显示"—"
   - And 不显示错误数值，不误导用户
4. **数据版本戳不匹配**：
   - When 一键更新完成后，前端缓存的版本戳与后端不匹配
   - Then 前端自动清空watchExtra缓存，重新获取数据
   - And 用户看到的是最新数据

**边界条件**：
1. **新基金首次上榜**：新基金的m3/m6/y1可能为None，重排榜单时用净值序列计算，抓取补充数据阶段更新到funds表
2. **基金从榜单掉下来**：该基金的2年历史净值保留30天，30天后清理到92天
3. **同时在榜单和自选**：只计算一次完整指标，避免重复计算
4. **卡玛比率分母为0**：近2月最大回撤为0时，卡玛比率返回None，不显示无穷大
5. **波动率数据不足**：年化波动率至少需要60天数据，下行波动率至少需要30天下跌日数据

**UI/数据规范**：
- 三个页面的指标显示格式一致：百分比保留2位小数，比率保留2位小数
- 数据不足时显示"—"，颜色为灰色（--text-tertiary）
- 卡玛比率、夏普比率等风险调整指标使用相同的颜色规范
- 数据字段：funds表包含m1/m3/m6/y1/max_dd/vol/down_vol/down_sharpe/calmar等指标
- 数据版本戳存储在settings表，key为data_version

#### 链路 D：数据源集成与降级机制（v2.11.4 起：pingzhongdata 主源）

> **⚠️ v2.11.4 数据源策略调整（现行）**：经 15 只样本测速，主源由同花顺改为 **pingzhongdata**（203ms/次 + 一次返回全史 2314 点），**天天基金网兜底**（430ms/60点）。**同花顺 API 已禁用** —— `collector/hithink_client.py` 依赖 `requests` 但 `requirements.txt` 未声明、运行时未安装，导致 `_get_hithink_client()` 返回 None、`get_fund_nav_items` 静默降级到天天基金（"假源"，测速中同花顺延迟/点数与天天完全相同即实证）；且即便修复 432ms 仍慢于 pingzhong，无保留价值。下方 v2.9.10/v2.9.14 的"同花顺主源/三数据源"描述为**历史演进记录**，已被本调整取代。预期阶段1抓净值从 17.5min 降至约 2.5min（~7×提速）。

**功能描述**：v2.9.10 起接入同花顺官方 API、v2.9.14 升级三数据源架构（历史）；**v2.11.4 起现行策略为 pingzhongdata 主源 + 天天基金网兜底，同花顺禁用**，覆盖**净值抓取、持仓抓取、基金基本信息**三大核心数据获取场景。支持**并行抓取**（缺口>1000只时 pingzhong 主源单池并发，workers=12）和**数据准确性验证**（异常值检测+日期连续性检查），主源返回空自动降级兜底，确保数据完整性和系统稳定性。系统监控页面实时展示数据源状态。

**核心架构（v2.11.4 现行）**：
1. **主源**：pingzhongdata（单次请求返回全量净值序列 ~2314 点，测速 203ms/只最快，并发≤12，间隔0.1秒）
2. **兜底源**：天天基金网（AkShare/爬虫，主源返回空时降级，并发≤8，间隔0.08秒，430ms/60点需翻页）
3. **同花顺 API（已禁用）**：`SOURCE_CONFIG["hithink"].enabled=False` —— 缺 `requests` 依赖静默降级天天基金（假源），且慢于 pingzhong；`config.use_hithink_as_primary` 标志仍存在但已失效
4. **降级链**：`SOURCE_PRIORITY=["pingzhong","eastmoney"]`，`fetch_one` 主源返回空则按链依次兜底，返回值带 `used_source`
5. **并行抓取**：`modules/nav/multi_source_fetcher.py::fetch_parallel()`，缺口>1000只触发；**v2.11.4 废弃旧三源等量分组 `codes[0::3]/[1::3]/[2::3]`**，统一 pingzhong 主源单池并发；`interval` sleep 移入 worker（抓取后限速）不再阻塞 `as_completed` 收集循环
6. **单源路径（日常增量 gap<1000）**：`fetcher.py::_fetch_with_pingzhong` —— 补全型走 pingzhong 全史、增量型转天天 `fetch_nav_range` 精确补缺口（省带宽），失败均降级天天
7. **数据准确性验证**：异常值检测（单日涨跌幅>±10%/净值为0/连续5天不变）+ 日期连续性检查（间隔>7天标记）
8. **统一适配层**：`modules/fund/pingzhong.py`（主源）+ `modules/nav/fetcher.py::fetch_nav_history`（兜底），统一输出 `[{date,ljjz,dwjz}]`
9. **状态监控**：`/api/admin/data-source-status`接口实时返回数据源可用性，前端系统监控页面展示

**覆盖的数据获取场景**：
| 场景 | 主源函数 | 第二源 | 备用源函数 | 调用位置 |
|------|---------|--------|-----------|---------|
| 净值抓取（增量） | `get_fund_nav_items()` | - | `fetch_nav_incremental()`内置降级 | `modules/nav/fetcher.py` |
| 净值抓取（全量补全） | `get_fund_nav_items()` | `fetch_pingzhong()` | `fetch_nav_history()` | `modules/nav/multi_source_fetcher.py` |
| 多源并行抓取 | 三源同时 | - | - | `modules/nav/multi_source_fetcher.py::fetch_parallel()` |
| 持仓抓取 | `get_fund_holdings_simple()` | - | `fetch_holdings_w()` | `modules/common/pipeline.py`的`_fetch_top_holdings()` |
| 基金基本信息 | `get_fund_profile()` | - | `fetch_basic()` | `modules/fund/profile.py`的`fetch_basic()` |

**正常路径（Given-When-Then）**：
- Given 用户已登录，同花顺API Key已配置，网络正常
- When 用户点击「一键更新数据」
- Then FetchManager执行八阶段流程
- And 阶段2「抓净值」调用`fetch_nav_incremental()`，内部优先调用同花顺API获取净值
- And 同花顺API返回数据后，转换为现有格式（date, ljjz, dwjz），数据入库（nav_history表）
- And 阶段6「抓持仓」调用`_fetch_top_holdings()`，内部优先调用同花顺API获取前十大持仓
- And 同花顺持仓API返回`[(股票名, 占比%), ...]`格式数据，用于计算持仓主题和写入funds表stocks字段
- And 基金详情/弹窗请求基本信息时，`fetch_basic()`优先调用同花顺API获取规模和成立日期
- And 同花顺基本信息API返回规模（元）和成立日期（毫秒时间戳），自动转换为亿元和YYYY-MM-DD格式
- And 数据断言：nav_history表新增当日净值，funds表stocks/themes字段更新，基金详情显示正确的规模和成立日期
- And 日志显示「使用同花顺主源，调整并发数为5，请求间隔0.2秒」

**异常路径**：
1. **同花顺API网络错误（净值/持仓/基本信息）**：
   - When 同花顺API请求失败（网络超时/连接错误）
   - Then 对应场景自动降级到天天基金网获取数据
   - And 记录警告日志「同花顺{净值/持仓/基本信息}抓取失败 {code}: {error}，降级到天天基金网」
   - And 用户无感知，数据正常更新
2. **同花顺API限流**：
   - When 同花顺API返回限流错误（4001错误码）
   - Then 指数退避重试（最多3次），仍失败则降级到天天基金网
   - And 记录警告日志，不影响其他基金
3. **同花顺API返回空数据**：
   - When 同花顺API返回空数据或数据格式错误
   - Then 降级到天天基金网获取数据
   - And 记录警告日志，不使用空数据覆盖现有数据
4. **同花顺API Key无效**：
   - When 同花顺API Key无效或过期
   - Then 健康检查失败，标记同花顺不可用
   - And 所有数据获取场景自动使用天天基金网备用源
   - And 记录错误日志，系统监控页面显示「降级中」
5. **备用源也失败**：
   - When 同花顺和天天基金网都失败
   - Then 该基金标记为抓取失败，记录错误日志
   - And 持仓抓取失败时用基金名称推断主题兜底，避免上榜基金themes为空
   - And 继续处理其他基金，不中断整个更新流程
6. **持仓数据为空（ETF/指数基金）**：
   - When ETF/指数基金没有股票持仓数据，同花顺返回空列表
   - Then 不降级（空数据是正常情况），直接用基金名称推断主题
   - And funds表stocks字段为空，themes字段为名称推断结果

**边界条件**：
1. **并发控制**：使用同花顺作为主源时，自动降低并发数（12→5）和增加请求间隔（0.08s→0.2s），避免触发同花顺限流。使用天天基金网时保持原有并发数
2. **数据格式统一**：
   - 净值：毫秒时间戳→YYYY-MM-DD，thscode→6位代码，格式统一为（date, ljjz, dwjz）
   - 持仓：同花顺返回dict列表→转换为`[(股票名, 占比%), ...]`元组列表，与天天基金网格式一致
   - 基本信息：规模（元）→亿元（除以1亿），成立日期（毫秒时间戳）→YYYY-MM-DD
3. **数据库表结构不变**：同花顺数据已适配为现有格式，nav_history/funds表结构无需任何变动，下游榜单计算、缓存机制、增量更新逻辑完全不受影响
4. **可配置开关**：通过环境变量`USE_HITHINK_AS_PRIMARY=false`可临时禁用同花顺主源，全部使用天天基金网备用源
5. **可用性缓存**：同花顺可用性检查结果缓存，避免每次请求都做健康检查。配置变更后可调用`reset_hithink_cache()`重置缓存
6. **API Key管理**：API Key存储在`backend/config.py`的`hithink_api_key`属性中，也可通过环境变量`HITHINK_API_KEY`覆盖。禁止在日志或前端输出API Key
7. **持仓主题兜底**：持仓抓取失败或为空时，自动用基金名称推断主题（`sector.infer_themes()`），确保上榜基金themes不为空
8. **基本信息缓存**：`fetch_basic()`结果走24h LRU缓存，同花顺和天天基金网的结果都缓存，避免重复请求
9. **数据源状态接口**：`GET /api/admin/data-source-status`返回`{hithink_available, hithink_as_primary, fallback}`，前端系统监控页面每30s自动刷新
10. **v2.9.14 三数据源架构**：从两数据源（同花顺+天天基金）升级为三数据源（同花顺+pingzhongdata+天天基金）。pingzhongdata单次请求可获取全量净值序列，速度快（0.03-0.2秒/只），适合全量补全场景。
11. **v2.9.14 多源并行抓取**：缺口>1000只时自动触发三源并行，把基金分成3组同时抓取，加速3倍。单数据源模式下仍使用同花顺主源+天天基金降级。多源并行模块：`modules/nav/multi_source_fetcher.py::fetch_parallel()`。
12. **v2.9.14 数据准确性验证**：抓取后自动进行三项验证：①异常值检测（单日涨跌幅>±10%、净值为0/负数、连续5天不变）；②日期连续性检查（间隔>7天标记为可能缺失）；③多源交叉验证（可选，匹配率≥90%认为通过，采用最佳数据源）。异常数据记录警告日志，不影响主流程。
13. **v2.9.14 历史数据补全**：`fetch_nav_incremental`增加`min_history_days`参数，历史数据不足250天的基金自动触发补全。部署时第一次运行全部基金触发补全，后续运行只抓增量。补全逻辑合并到增量抓取阶段，不再是独立阶段。

**UI/数据规范**：
- 数据源状态卡片：「我的→系统监控」第一行统计卡片第5张，显示：
  - 标题：「数据源状态」
  - 主值：同花顺可用时显示「同花顺正常」（绿色），不可用时显示「降级中」（橙色）
  - 副值：「主源: 同花顺/备用源 / 备用: AkShare + 天天基金网」
  - 随系统监控页面30s自动刷新
- 一键更新日志：显示「使用同花顺主源，调整并发数为5，请求间隔0.2秒」
- 降级日志：显示「同花顺{净值/持仓}抓取失败 {code}: {error}，降级到天天基金网」
- 数据字段：
  - nav_history表保持现有结构（code, date, ljjz, dwjz）
  - funds表stocks字段格式为`[[股票名, 占比], ...]`JSON数组
  - funds表themes字段格式为`[[主题名, 权重], ...]`JSON数组
- 配置文件：`backend/config.py`新增`hithink_api_key`和`use_hithink_as_primary`属性
- API接口：`GET /api/admin/data-source-status`返回数据源状态

### 3.9 交易记录导入 / OCR 链路

**功能描述**：支持Excel/CSV导入交易记录和截图OCR识别，导入后持仓汇总/止盈汇总/详情同步更新。

**正常路径（Given-When-Then）**：
- Given 用户已登录，有交易记录Excel/CSV文件

- And 成功/跳过/错误计数返回，前端展示错误明细
- And 导入记录后持仓汇总/止盈汇总/详情同步更新
- And 数据断言：investment_records表新增导入的记录，portfolio表汇总更新

**异常路径**：
1. **文件格式错误**：
   - When 上传非Excel/CSV文件或文件损坏
   - Then 返回400错误，提示「文件格式错误，请上传Excel/CSV文件」
2. **表头不匹配**：
   - When Excel表头无法归一化（缺少必要列如日期/金额/份额）
   - Then 返回400错误，提示「表头不匹配，请检查列名」，不导入任何数据

   - When 部分行日期格式错误/净值缺失/份额金额互算失败
   - Then 成功的行导入，失败的行跳过，前端展示错误明细（行号+原因）
4. **OCR识别失败**：
   - When 截图OCR识别失败（图片模糊/非交易截图）
   - Then 返回错误提示，不生成待确认字段

**边界条件**：
1. **截图OCR两段式**：只上传图片返回待确认字段，人工确认后仍走普通添加接口（OCR本身不落库）
2. **重复导入无去重**：重复导入同一文件会重复计数（无去重），需用户自行确认
3. **日期多格式**：支持YYYY-MM-DD/YYYY/MM/DD/MM-DD-YYYY等多种日期格式
4. **净值多级兜底**：净值缺失时从nav_history/实时源兜底，仍缺失则该行跳过
5. **份额金额互算**：只有金额时按净值计算份额，只有份额时按净值计算金额

**UI/数据规范**：
- 导入入口：持仓页「导入」按钮，支持Excel/CSV文件选择
- 导入结果：成功/跳过/错误计数，错误明细列表（行号+原因）

- 数据字段：investment_records含code/name/date/type(buy/sell)/amount/shares/nav/profit_target

#### 链路 B：算法配置

**功能描述**：支持调整抗跌/收益权重、攻防榜参数、超跌筑底榜参数，修改后需重算榜单生效。

**正常路径（Given-When-Then）**：
- Given 用户已登录，进入「我的→算法」
- When 用户调整抗跌/收益权重（如抗跌0.6/收益0.4）
- And 点击「保存」
- Then 调用`POST /cfg/algo`持久化
- And 全站综合分 = 抗跌分×权重 + 收益分×权重 重算
- And 榜单排序、卡片评分、推荐信号全部受影响
- And 数据断言：cfg表algo字段更新为新权重

**异常路径**：
1. **权重和不为1**：
   - When 抗跌权重+收益权重≠1
   - Then 返回422错误，提示「权重之和必须为1」，不保存
2. **参数越界**：
   - When 参数超出预设范围（如cd_crash_k>4.0）
   - Then 返回422错误，提示「参数超出范围」，不保存
3. **保存失败**：
   - When POST /cfg/algo调用失败
   - Then toast显示「保存失败，请稍后重试」，参数不更新

**边界条件**：
1. **影响面**：改权重后榜单评分变化、详情弹层评分明细与算法说明一致；改回默认后恢复
2. **配置校验**：非法权重/越界参数返回422
3. **攻防榜参数（6组共14个参数）**：
   - 捕获率口径：上涨日阈值(默认0.5%)、下跌日阈值(默认-0.5%)
   - 高弹性：Beta下限(默认1.3)、上涨捕获率下限(默认1.3)
   - 攻守兼备：Beta下限(0.5)、Beta上限(1.1)、捕获率差下限(0)、最大回撤下限(-10%)
   - 强抗跌：下跌捕获率上限(0.7)、最大回撤下限(-5%)
   - 反弹先锋：20日跌幅上限(-5%)、5日涨幅下限(0%)
   - 修改后需点击「立即重算榜单」生效
4. **超跌筑底榜参数（1组共6个参数）**：
   - cd_crash_k（急跌强度系数K，默认2.0，范围1.0~4.0）
   - cd_accel_ratio（加速下跌倍数，默认1.5，范围1.0~3.0）
   - cd_low_dd（低位回撤阈值，默认-20%，范围-40%~-5%）
   - cd_low_pct（低位分位阈值，默认20%，范围5%~50%）

### 3.14 持仓标签链路（v2.9.0 新增）

**目的**：确保基金卡片底部的持仓标签（themes）数据准确，区分真实持仓与名称推断，减少兜底标签比例。

#### 链路 A：标签生成优先级

**功能描述**：持仓标签采用三级降级机制：真实持仓抓取→基金名称推断→兜底标签，确保标签准确性。

**正常路径（Given-When-Then）**：
- Given 用户已登录，一键更新已完成
- When 查看基金卡片的持仓标签
- Then 优先显示真实持仓标签（如"半导体45%"）
- And 真实持仓抓取：调用天天基金接口fetch_holdings_w_full(code)获取前十大持仓（含股票代码），经holdings_themes()按概念匹配→东财行业兜底→"其他"聚合，返回最多3个主题标签（含持仓百分比）
- And 若持仓抓取失败，降级1：infer_themes(name)按指数名>行业/主题词>板块兜底三级匹配
- And 若名称无法匹配，降级2：标记为"核心资产"（兜底标签）
- And 数据断言：榜单前20只基金中，"核心资产"兜底标签占比应<30%

**异常路径**：
1. **持仓抓取失败**：
   - When fetch_holdings_w_full()调用失败（网络错误/接口限流）
   - Then 降级为名称推断，若名称推断也失败则降级为兜底标签
   - And 记录警告日志，不影响其他基金
2. **持仓占比过低**：
   - When 十大持仓合计<5%（ETF联接基金主要持有母基金，股票持仓是噪音）
   - Then 返回空标签，不显示持仓标签
3. **重复抓取**：
   - When stocks字段非空的基金重复抓取
   - Then 断点续传：检查stocks字段非空则跳过，避免重复抓取

**边界条件**：
1. **三级降级机制**：真实持仓（优先）→名称推断（降级1）→兜底标签（降级2）
2. **断点续传**：_fetch_top_holdings检查stocks字段非空则跳过，避免重复抓取
3. **持仓占比阈值**：十大持仓合计<5%时返回空（ETF联接基金主要持有母基金，股票持仓是噪音）
4. **验证标准**：榜单前20只基金中，"核心资产"兜底标签占比应<30%；超过则说明持仓抓取失败，需重新运行一键更新

**UI/数据规范**：
- 持仓标签：最多3个，含持仓百分比（如"半导体45%"），字号10px，padding 1px 6px，圆角4px，不同行业不同颜色

- 数据字段：themes为JSON数组，每个元素含name和percent，stocks为十大持仓JSON
- 关键词规则：SECTOR_RULES（板块推断，30+类）、THEME_WORDS（细分主题，40+类）、INDEX_RULES（指数细分，20+类）

2. **双写同步**：funds.themes和rank_snapshots.meta.themes都要更新，确保榜单页显示最新标签
3. **新增基金自动生成**：新增基金后标签应自动生成（名称推断或实时兜底抓取）
4. **刷新页面**：重算后需刷新页面才能看到最新标签

**UI/数据规范**：
- 重算脚本：scripts/backfill_themes_targeted.py
- 重算范围：当前榜单rank_snapshots+自选watchlist+持仓portfolio
- 同步字段：funds.themes和rank_snapshots.meta.themes
- 标签格式：JSON数组，每个元素含name和percent，最多3个

#### 链路 C：标签准确性验证

**功能描述**：验证持仓标签的准确性，包括榜单页/自选/持仓页一致性、详情弹层一致性、兜底标签占比。

**正常路径（Given-When-Then）**：
- Given 用户已登录，一键更新已完成
- When 抽查榜单前10只基金
- Then 持仓标签应与基金实际持仓行业一致，不应出现"核心资产100%"兜底
- And 自选和持仓中的基金标签应与榜单页同基金一致（同一数据源）
- And FundDetailModal底部的主题标签应与卡片一致
- And 无股票持仓的基金（债券/货币/空仓）应显示"核心资产100%"（当前实现，非"灵活配置"）
- And 榜单前20只中"核心资产"占比应<30%，超过则说明持仓抓取失败

**异常路径**：
1. **标签不一致**：
   - When 同一只基金在榜单/自选/持仓页标签不一致
   - Then 视为数据缺陷，需检查funds.themes和rank_snapshots.meta.themes是否同步
2. **详情弹层标签不一致**：
   - When FundDetailModal底部的主题标签与卡片不一致
   - Then 视为数据缺陷，需检查详情弹层的标签数据源
3. **兜底标签占比过高**：
   - When 榜单前20只中"核心资产"占比≥30%
   - Then 视为持仓抓取失败，需重新运行一键更新或backfill_themes_targeted.py

**边界条件**：
1. **跨页面一致性**：榜单/自选/持仓页同一只基金标签一致（同一数据源）
2. **详情弹层一致性**：FundDetailModal底部的主题标签与卡片一致
3. **无股票持仓基金**：债券/货币/空仓基金显示"核心资产100%"（当前实现）
4. **兜底标签占比阈值**：榜单前20只中"核心资产"占比应<30%

**UI/数据规范**：
- 标签显示：最多3个，含持仓百分比，字号10px，不同行业不同颜色
- 兜底标签：灰色背景+灰字，与真实持仓标签区分
- 验证方法：抽查榜单前10只，跨页面对比，详情弹层对比
- 数据字段：themes为JSON数组，每个元素含name和percent

### 6.3 设计约定（与旧 E2E 的差异）



1. **鉴权**：页面经 `addInitScript` 注入 `wb_api_key`（等价线上 `?k=` 激活），浏览器端请求自动带 `X-Touyan-Key`；API 辅助请求头也用 `X-Touyan-Key`。

2. **强断言**：每步断言具体文案 / 列表项 / 份额 / 状态 / 服务端落库，禁止 `if (await x.isVisible())` 跳过与恒真断言。

3. **数据清理走 API**（beforeEach/afterEach），不替代被测 UI 动作。

4. **卖出用例**用「按份额卖出 500 份」而非全部卖出 —— 全部卖出会清仓删除 portfolio 行，导致记录列表不可见，断言不稳定。

5. **左滑模拟**鼠标拖拽且终点移出卡片，避免浏览器把 mousedown+mouseup 合成 click 误开基金详情弹窗（anti-modal 会拦截后续操作）。

6. **完整缓存控制方案（三层防护）**
   - 目的：防止版本更新后用户看到旧版本或旧数据
   - 实现：
     - HTTP层：带hash的JS/CSS长期缓存，index.html no-cache（已有）
     - HTML层：index.html添加 `Cache-Control: no-cache,no-store,must-revalidate` + `Pragma:no-cache` + `Expires:0`
     - 应用层：`src/utils/version.ts` 定义 `APP_VERSION='2.9.5'`，main.ts启动时调用 `checkAndMigrateVersion()`，版本不匹配时自动清除业务缓存（保留用户设置）
   - 发版流程：修改 `APP_VERSION` → 构建 → 部署，无需改其他代码

**关键教训：**
- localStorage缓存必须有版本控制，否则旧数据会污染新功能
- 缓存过滤条件不能只检查几个字段，要检查关键字段（如d1）是否存在
- 静态资源缓存控制需要三层：HTTP头 + HTML meta + 应用层版本检测
