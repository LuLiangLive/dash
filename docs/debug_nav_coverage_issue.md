# 净值数据覆盖不足问题排查记录与思维逻辑

**问题ID**: CHG-20260907-053
**排查时间**: 2026-09-07
**排查人员**: AI助手
**问题等级**: HIGH
**最终版本**: 2.9.60

---

## 一、问题现象

用户报告：一键更新后，92.7%（5345只）基金只有63天（3个月）净值数据，而非预期的250天（1年），导致三个月/六个月/一年涨跌幅、抗跌分析、回测等指标无法正确计算。

**关键数据点**:
- 总基金数: 6052只
- >=250天: 仅250只（4.1%）
- 60-99天: 5610只（92.7%）
- 绝大多数正好是63天
- 63天基金的最早日期统一为2026-06-09（正好从2026-09-04往前推3个月/63个交易日）

---

## 二、排查思维逻辑（一条一条往下排）

### 阶段1：假设是抓取参数问题 → 验证后排除

**假设1**: `page_size=60`硬编码导致只抓60天
- **排查动作**: grep搜索`days=60|page_size=60`
- **发现**: pipeline.py第595行存在`fetcher.fetch_nav_many(todo, page_size=60, workers=16,...)`
- **修复**: page_size=60→250, max_pages=5→15
- **验证**: 单独测试`fetch_nav_history(page_size=250, max_pages=15)`返回260条数据
- **结果**: ❌ 两次全量重抓后，问题仍然存在，92%基金还是只有63天

**思维逻辑**: 先找最明显的硬编码参数，因为63天和60天很接近，很可能是page_size的问题。但是修改后问题仍然存在，说明不是这个原因，需要继续往下排。

---

### 阶段2：假设是数据源本身数据不足 → 验证后排除

**假设2**: 某些基金的数据源本身只返回63天数据
- **排查动作**: 单独测试三个数据源
  - 同花顺API `range=year`: 000241返回243条（2025-09-04 ~ 2026-09-04）
  - pingzhong: 000241返回3193条全量历史数据（2013-08-01 ~ 2026-09-04）
  - 天天基金: 000241返回260条
- **结果**: ❌ 三个数据源都能返回250天以上数据，不是数据源本身的问题

**思维逻辑**: 既然参数改了还不行，那可能是数据源本身数据不足。单独测试每个数据源，发现都能返回250天以上数据，排除这个假设。

---

### 阶段3：假设是健康检查逻辑错误 → 验证后排除

**假设3**: 健康检查函数错误地认为63天数据是"健康"的，导致不重新抓取
- **排查动作**: 测试`_batch_nav_health`函数处理6000只基金
- **发现**: 5888只被正确判断为不健康，133只健康。只有63天数据的基金都被正确判断为不健康。
- **结果**: ❌ 健康检查逻辑是正确的，不是这个原因

**思维逻辑**: 既然数据源没问题，那可能是健康检查逻辑错误，认为已有数据是健康的，所以不重新抓取。测试后发现健康检查逻辑是正确的，63天数据都被正确判断为不健康，排除这个假设。

---

### 阶段4：假设是抓取函数本身有bug → 验证后排除

**假设4**: `fetch_nav_incremental`函数在处理大量基金时有bug
- **排查动作**: 测试`fetch_nav_incremental`函数处理10只只有63天数据的基金
- **发现**: 待抓10只（增量型3只，补全型7只，跳过0只），7只补全型基金都抓取到了243-260条数据，总抓取1789条，平均178.9条/只。
- **结果**: ❌ `fetch_nav_incremental`函数本身是正常的，不是这个原因

**思维逻辑**: 既然健康检查没问题，那可能是抓取函数本身有bug。单独测试抓取函数处理10只基金，发现都能正常抓取250天以上数据，排除这个假设。

---

### 阶段5：假设是数据入库函数有bug → 验证后排除

**假设5**: `merge_navs_to_db`或`bulk_upsert_navs`函数在处理大量数据时有bug，只入库了部分数据
- **排查动作**: 手动测试`merge_navs_to_db`函数处理000241
- **发现**: 测试前63条，抓取260条，merge后260条，日期范围2025-08-13~2026-09-07，完全正常。
- **结果**: ❌ 数据入库函数本身是正常的，不是这个原因

**思维逻辑**: 既然抓取函数没问题，那可能是数据入库函数有bug，只入库了部分数据。单独测试入库函数，发现能正常入库260条数据，排除这个假设。

---

### 阶段6：假设是多数据源并行模式有bug → 验证后排除

**假设6**: 多数据源并行模式在处理大量基金时有bug
- **排查动作**: 检查`fetch_parallel`、`fetch_one`、`validate_data_quality`函数的完整实现
- **发现**: 所有函数逻辑都是正确的，`validate_data_quality`会在数据不足时自动用其他数据源补全
- **结果**: ❌ 多数据源并行模式本身是正常的，不是这个原因

**思维逻辑**: 既然单个函数都没问题，那可能是多数据源并行模式在处理大量基金时有bug。仔细检查所有相关函数的实现，发现逻辑都是正确的，排除这个假设。

---

### 阶段7：关键突破 — 发现数据丢失现象

**关键观察**: 
- task_logs显示id=18的collector任务抓取了**2,874,532条**数据
- 但是nav_history表中实际只有**502,485条**
- **有2,372,047条数据丢失了**！

**思维逻辑**: 到这里，所有单个函数都测试过了，都是正常的。但是数据量对不上，说明数据在某个环节丢失了。这时候需要换一个思路，不是看单个函数，而是看整个一键更新的流程，看看数据是在哪里丢失的。

---

### 阶段8：全程监控 — 定位数据丢失的时间点

**排查动作**: 
1. 清空nav_history表
2. 在后台启动监控脚本，每30秒检查一次数据量
3. 触发一键更新，全程监控数据量变化

**关键发现**:
- 0-690秒: 数据量从0增加到1,280条（指数基金数据），然后保持不变
- 690秒时: 数据量突然从1,280条增加到**1,438,590条**（净值抓取完成，一次性入库）
- 811秒时: 数据量增加到**1,544,199条**（阶段3补充抓取完成）
- 841秒时: 数据量突然从1,544,199条下降到**509,779条**！（有1,034,420条数据被删除了！）

**思维逻辑**: 既然数据丢失了，那就全程监控数据量的变化，看看数据是在哪个时间点丢失的。通过监控发现，数据量在841秒时突然下降了100多万条，说明是在一键更新的某个阶段主动删除了数据！

---

### 阶段9：定位删除数据的代码

**排查动作**: 
1. 检查一键更新的完整日志
2. 搜索"清理旧净值数据"、"删除.*90天前"等关键词

**关键发现**:
日志中明确记录：
```
[阶段3/6] 清理旧净值数据: 删除1034420条90天前的数据 (上榜+自选344只保留2年)
```

**根本原因**: 
`fetch_manager.py`第491-494行：
```python
# 清理旧数据: 上榜+自选基金排除(保留2年), 其他基金清理90天以上
_cleaned = cleanup_old_navs(days=90, verbose=True, exclude_codes=_keep_codes)
```

一键更新在阶段3/6会调用`cleanup_old_navs(days=90, ...)`函数，**自动删除90天前的净值数据**，只保留上榜+自选的344只基金的2年数据。

**思维逻辑**: 既然数据是在某个阶段被主动删除的，那就检查一键更新的日志，看看是哪个阶段删除的。通过搜索关键词，找到了"清理旧净值数据"的日志，然后定位到具体的代码，终于找到了根本原因！

---

## 三、根本原因总结

**根本原因**: 一键更新在阶段3/6会自动调用`cleanup_old_navs(days=90, ...)`函数，删除90天前的净值数据，只保留上榜+自选的344只基金的2年数据。

**为什么之前没有发现**:
1. 这个清理功能是v2.5.4版本添加的，目的是控制数据库大小
2. 之前的净值抓取可能本身就只抓90天，所以清理后看不出问题
3. 这次修改了page_size=250，抓取了一年的数据，但是清理阶段又把90天前的数据删掉了，导致问题暴露出来
4. 所有单个函数测试都是正常的，因为清理是在一键更新的整体流程中执行的，单独测试某个函数不会触发清理

**数据流向**:
```
净值抓取阶段: 抓取2,874,620条（平均每只477天）
    ↓
阶段3补充抓取: 增加到1,544,199条（注意：这里数字对不上，因为有重复数据被upsert了）
    ↓
清理旧数据阶段: 删除1,034,420条90天前的数据
    ↓
最终数据库: 509,779条（92%基金只有63天数据）
```

## 四、修复方案

**修改文件**: `backend/modules/common/fetch_manager.py`第491-494行

**修改内容**:
```python
# 修改前
_cleaned = cleanup_old_navs(days=90, verbose=True, exclude_codes=_keep_codes)

# 修改后
_cleaned = cleanup_old_navs(days=365, verbose=True, exclude_codes=_keep_codes)
```

**修复逻辑**:
- 普通基金: 保留365天（一年）的数据，满足年涨跌幅、抗跌分析、回测等指标的计算需求
- 上榜+自选基金: 通过`exclude_codes`参数排除，仍然保留2年数据
- 数据库大小: 从约50万条增加到约150万条，在可接受范围内

## 五、经验教训与思维逻辑总结

### 1. 排查方法论

**一条一条往下排的思维逻辑**:
1. **先找最明显的问题**: 硬编码参数、明显的bug
2. **然后逐个排除假设**: 数据源问题 → 健康检查问题 → 抓取函数问题 → 入库函数问题 → 多源并行问题
3. **当所有单个函数都正常时，换思路看整体流程**: 数据是在哪里丢失的？
4. **全程监控关键指标**: 数据量变化、时间点定位
5. **通过日志定位具体操作**: 搜索关键词、检查完整日志

### 2. 容易踩的坑

**坑1: 只看单个函数，不看整体流程**
- 所有单个函数测试都正常，但是整体流程有问题
- 教训: 当单个函数都正常时，一定要看整体流程，看看数据是在哪里丢失的

**坑2: 忽略清理/删除操作**
- 只关注抓取和入库，忽略了清理和删除操作
- 教训: 数据量对不上时，一定要检查是否有删除操作

**坑3: 被表面现象迷惑**
- 63天数据，最早日期统一为2026-06-09，看起来像是抓取参数的问题
- 实际上是清理操作删除了90天前的数据
- 教训: 表面现象可能误导，需要深入排查根本原因

### 3. 神经网络更新要点

**需要记住的排查模式**:
- 当数据量对不上时，先全程监控数据量变化，定位丢失的时间点
- 然后检查该时间点对应的一键更新阶段
- 最后搜索该阶段的日志，定位具体的操作代码

**需要记住的代码位置**:
- `fetch_manager.py`第491-494行: 清理旧净值数据的调用
- `fund_metrics.py`第304-363行: `cleanup_old_navs`函数的实现

**需要记住的业务逻辑**:
- 一键更新有6个阶段，阶段3/6会清理旧净值数据
- 普通基金默认保留90天（已改为365天），上榜+自选基金保留2年
- 这个清理功能是v2.5.4版本添加的，目的是控制数据库大小
