3. 需确认的字段清单 (引用复杂或有间接引用)
================================================================================

3.1 up7 - 7日内上涨天数
    - rank_full._build_item包含up7(注释"必须保留"因旧版引用)
    - 但scoring_v3 dual_score不用up7; rank_full主流程评分不依赖up7
    - 仅旧版is_candidate(稳涨形态)、reco_score(结构分)、composite_score(趋势+稳健分)使用
    - 若删除is_candidate/composite_score, up7仅reco_score使用
    - reco_score被recompute_ad计算并写入funds.reco_score, rank_full透传
    - **结论: up7本身需保留(metrics计算), 但meta中的up7可考虑删除(前端/md_builder不读)**

3.2 reco_score - 六维推荐分
    - recompute_ad计算并写入funds.reco_score
    - rank_full._build_item透传到meta但不用于排序
    - md_builder._reco_line作为tscore fallback第2顺位
    - 旧版build_ranks开仓榜/推荐榜用于排序
    - **结论: 需确认前端是否读取meta.reco_score; 若仅md_builder使用则随旧版废弃**

3.3 dd20 vs dd_from_hi - 命名不一致
    - funds表有独立dd20列, pipeline写入m.get('dd_from_hi')的值(别名)
    - rank_full meta用标准名dd_from_hi, 不含dd20
    - md_builder读it.get('dd20')→从rank_full meta取恒None
    - compare.py从funds表读dd20→有值
    - **结论: dd20是dd_from_hi的旧别名; funds列可合并; md_builder的dd20读取应改为dd_from_hi**

3.4 dd_from_high (超跌筑底) vs dd_from_hi (标准)
    - dd_from_high: 超跌筑底榜专用, 距60日高点回撤
    - dd_from_hi: 标准字段, 距历史高点回撤
    - 命名极近但含义不同, 易混淆
    - **结论: 建议重命名为dd_from_60high以区分**

3.5 nav列 - pipeline写入疑似bug
    - pipeline L781: "nav": fm["navs"][-1] if fm.get("navs") else m.get("ret2m")
    - else分支fallback到ret2m(近2月收益)明显错误, 应为None
    - rank_full._build_item从f['navs'][-1]取nav, 不从funds.nav读
    - **结论: 需确认funds.nav列的实际消费方; 修复pipeline fallback**

3.6 suggest列
    - pipeline写空dict{}
    - fund_service/watch_fetch读取但内容恒为空
    - **结论: 疑似遗留字段, 需确认是否有前端消费**

3.7 yindie列
    - v2.10.0后pipeline不写入
    - recompute_ad对上榜+自选基金写入detect_yindie_deep结果
    - rank_full meta不含yindie
    - main.py有引用(需确认具体用途)
    - **结论: 需确认yindie是否仍有前端展示需求**

3.8 score列权重不一致
    - recompute_ad写入 earn*0.5+ad*0.5 (旧版50/50)
    - scoring_v3 dual_score = 收益42.5%+抗跌42.5%+卡玛15%
    - rank_full._build_item优先用_unified dual(scoring_v3), 降级才用funds.score
    - **结论: 需统一recompute_ad的score计算为scoring_v3 dual_score**

3.9 panel_score()函数
    - 主流程自选榜调用panel_score('自选算法榜单')→watch_score_light
    - 稳涨/强趋势/ETF/抗跌/开仓分支仅旧版build_ranks使用
    - **结论: 可精简为仅保留自选算法榜单分支, 其余随旧版删除**

3.10 sharpe (普通夏普)
    - watch_score_light使用(夏普9分)
    - compare总结展示(从fund_detail stats取)
    - 与down_sharpe(下行夏普)不同
    - **结论: watch_score_light被主流程自选榜调用, sharpe需保留计算**

3.11 max_dn

    - 大量_*.py临时迁移脚本引用
    - **结论: 需确认scoring_v3中是否实际使用max_dn配置**

3.12 dn_ratio在compare中的读取

4. 旧版链路整体废弃可行性结论
   (ranking.build_ranks + scoring.composite_score + md_builder + html_service 整条链)
================================================================================

【结论: 可整体废弃, 但需分3步执行】

步骤1: 确认前端不依赖静态HTML
  - main.py L57导入fund_html_content用于首页静态渲染
  - 用户实际使用Vue前端(http://127.0.0.1:8000/#/market)
  - 需确认: 是否有外部用户/爬虫依赖 /api 或根路径的静态HTML
  - 若确认无依赖, 可删除main.py中的fund_html_content导入和路由

步骤2: 删除旧版榜单构建链
  - ranking.build_ranks() → 仅recompute_ranks.py调用
  - scoring.composite_score() → 仅panel_score旧分支调用
  - recommendation.is_candidate() → 仅build_ranks调用
  - panel_score()的稳涨/强趋势/ETF/抗跌/开仓分支 → 仅build_ranks调用
  - 以上可整体删除, 保留watch_score_light(自选榜在用)和panel_score的自选分支

步骤3: 删除静态渲染链
  - html_service.fund_html_content() → 仅main.py调用
  - md_builder.build_fund_markdown() → 仅html_service调用
  - rendering/fund_page.py render_fund_view() → 仅html_service调用
  - 若步骤1确认无依赖, 可整体删除rendering/目录和html_service.py

【不可删除的部分】
  - watch_score_light() → 主流程自选榜评分在用
  - reco_score() → recompute_ad计算推荐分在用
  - trend_status() → rank_full._build_item兜底在用
  - momentum_status() → rank_full动能衰减预警在用
  - reco_risk_tags_txt() → rank_full._build_item risk标签在用
  - ranker.calc_metrics() → 全系统指标计算基础

【风险提示】
  - md_builder中dd20/dd7/cs等字段的死读取不影响功能, 但删除md_builder后这些读取自然消除
  - rendering/card_renderer.py和rendering/markdown_parser.py可能被其他模块引用, 需单独确认
  - db.py中save_rank/get_ranks/latest_rank_date等函数可能同时服务于Vue前端API, 不可删除

5. scripts/recompute_ranks.py 对旧版的依赖情况
================================================================================

recompute_ranks.py 是旧版重算脚本, 完全依赖旧版链路:

【直接依赖】
- L21: import collector.ranker as ranker → 导入build_ranks/composite_score/watch_score_light等
- L22: from collector.pipeline import _prev_boards, _today
- L61: ranker.calc_metrics() → 指标计算(新版也在用, 非旧版专属)
- L102: ranker.composite_score(m) → 旧版综合分(可删除)
- L111: ranker.compute_scores_v2() → 已迁移到scoring_v3, 但函数本身仍可用
- L120: ranker.verdict_of() → 旧版持有结论(可删除)
- L127: UPDATE funds SET ad_score/earn_score/score/verdict/yindie/mdd/... → 写入verdict(死列)
- L139: ranker.build_ranks(funds_meta, prev_boards) → 旧版榜单构建(核心依赖)
- L144: db.save_rank() → 写入rank_snapshots

【与主流程的冲突】
- recompute_ranks用build_ranks生成的meta包含cs/dn_ratio/dd20等旧字段
- 主流程rank_full生成的meta不含这些字段
- 若运行recompute_ranks会覆盖rank_full的榜单数据, 导致字段不一致
- recompute_ranks的score用earn*0.5+ad*0.5, 与scoring_v3 dual_score(42.5/42.5/15)不一致

【建议】
- recompute_ranks.py应整体废弃或重写为调用rank_full.compute_all_panels()
- 若需保留"算法变更后重算"功能, 应调用fetch_manager的一键更新流程而非旧版build_ranks
- verdict列的写入应移除(死列)
- composite_score调用应移除

附录: collector/ 与 modules/ 版本关系
================================================================================

经确认, collector/目录下的ranking.py/scoring.py/recommendation.py均为v2.5.5架构重构后的
兼容层(re-export), 实际实现在modules/对应文件中:
- collector/ranking.py → from modules.rank.ranking import *
- collector/scoring.py → from modules.score.scoring import (具体函数)
- collector/recommendation.py → from modules.rank.recommendation import *

因此不存在"两套实现"问题, 主流程导入collector.ranker最终调用的是modules/中的实现。
collector/ranker.py本身包含calc_metrics等核心指标函数(非re-export), 是真正的实现层。
